### T02. Safe startup and preference reset — [page 11](https://betterdisplay.pro/guide/faq/general/reset-app-settings/)

- **BetterDisplay behaviour** (Free recovery workflow; referenced features retain their tiers): Holding Shift during launch enters Safe Mode and reports it. Startup skips virtual-screen auto-connections, brightness/other adjustment restoration and automatic custom EDID. It neither deletes saved devices nor permanently disables their rules. A problematic virtual screen can then be discarded in Settings → Displays with confirmation. Application → Advanced Settings & Privacy → Manage App Settings provides Export and confirmed Reset followed by restart; test defaults before restoring a suspect backup. A per-user preferences-domain deletion while the app is quit is the manual fallback, with export first. App reset leaves installed macOS display overrides intact. The separate advanced system-display reset removes system configuration, generated factory profiles, overrides and remembered displays and requests reboot. Do not use system reset for an isolated app rendering fault; collect versions, connection details and whether quitting restores the picture if defaults do not help.
- **FreeDisplay today**: 🟡 Partial. `--safe-mode` only feeds virtual-screen creation gating (`Apps/OpenDisplay/Sources/SettingsView.swift:52`, `Apps/OpenDisplay/Sources/VirtualDisplaysSettingsView.swift:25`). No Shift-launch-wide suppression or preference export/import/reset UI was found. Settings use JSON and other independent stores, not only UserDefaults (`Packages/TopologyCore/Sources/TopologyCore/SettingsStore.swift:7`, `Packages/TopologyCore/Sources/TopologyCore/DisplayRegistry.swift:31`). The existing `resetToDefaults` is a monitor factory-reset action, not an app reset (`Apps/OpenDisplay/Sources/AppModel.swift:2181`).
- **Implementation notes**: Public AppKit launch modifiers plus a single startup policy, versioned Foundation archive and atomic replacement; M. Inventory all stores before defining reset scope. System overrides require a separately reviewed privileged workflow; L/high risk, not a prerequisite for preference recovery.
- **Acceptance criteria**:
  - Shift launch suppresses every automatic mutation while retaining settings and showing recovery UI.
  - Export/reset/import round-trips settings; reset never sends DDC factory reset or deletes system overrides.
  - A reset preview lists affected stores and recovery remains possible with a malformed archive.

### T03. Settings portability and display identity — [page 23](https://betterdisplay.pro/guide/faq/general/transfer-settings/), [page 48](https://betterdisplay.pro/guide/faq/general/settings-lost-after-wake/)

- **BetterDisplay behaviour** (Free settings workflow; no separate tier stated): Export at Application → Advanced Settings & Privacy → Manage App Settings; back up the destination, import the file, then restart. Import replaces existing preferences. When identifiers differ, use the current display’s Additional Settings → Display Identification & Settings Transfer → Transfer display settings to select the prior disconnected record. Diagnose names/settings swapping by comparing the system UUID in Display Information before/after wake. Per-display identification can use Basic + extended + port on Apple silicon to distinguish identical panels; keep cabling consistent. Changing identification can create a new record and require transfer. The global default affects unseen displays only. Aliases do not establish identity and app matching does not change macOS UUIDs. Stable identities require investigating the particular restoration feature instead.
- **FreeDisplay today**: 🟡 Partial. Registry persistence, aliases, UUID fast path and fingerprint scoring exist (`Packages/TopologyCore/Sources/TopologyCore/DisplayRegistry.swift:67`, `:142`, `:178`). The model associates observations with those records (`Apps/OpenDisplay/Sources/AppModel.swift:589`), but group membership and many preferences still use observation IDs (`Packages/TopologyCore/Sources/TopologyCore/DisplayRegistry.swift:100`, `Packages/TopologyCore/Sources/TopologyCore/SettingsStore.swift:105`). There is no per-display matching-method selector, old-record transfer wizard or whole-settings archive UI. Display Information does not expose the UUID (`Apps/OpenDisplay/Sources/AppModel.swift:1045`); diagnostic exports do (`Providers/CoreGraphicsProvider/Sources/CoreGraphicsProvider/DiagnosticsBundle.swift:18`). A registry match alone does not prove all preference keys survive a changed UUID.
- **Implementation notes**: Public CoreGraphics/ColorSync identifiers, existing IOKit fingerprint reading, Foundation migration; M. Keep runtime CG IDs, OS UUIDs and app record IDs separate. Transfer must include groups, favorites and restoration ledgers without merging ambiguous identical monitors automatically.
- **Acceptance criteria**:
  - Changing a monitor UUID preserves or explicitly offers migration of all selected preferences.
  - Two identical monitors never silently exchange labels or controller settings.
  - Import reports unmatched records and preserves a destination backup.

### T04. Platform, source availability and distribution constraints — [page 12](https://betterdisplay.pro/guide/faq/general/windows-alternative/), [page 15](https://betterdisplay.pro/guide/faq/general/source-code/), [page 17](https://betterdisplay.pro/guide/faq/general/mac-app-store/)

- **BetterDisplay behaviour** (Free information): Current app source is private; the public repository serves releases/issues/discussions. The archived BetterDummy open-source branch is not current BetterDisplay. CLI and localization are separate public projects. BetterDisplay distributes directly because some features use private/undocumented APIs incompatible with App Store public-API requirements. Its Windows FAQ points to Twinkle Tray for supported DDC brightness, contrast, volume, power and hotkeys; DDC must be enabled and dock paths/features tested separately.
