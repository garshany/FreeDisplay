## Topics

### T01. Control vocabulary and reference navigation — [control](https://betterdisplay.pro/guide/technical-reference/control/) · [technical-reference](https://betterdisplay.pro/guide/technical-reference/) · [controller](https://betterdisplay.pro/guide/technical-reference/controller/)

- **BetterDisplay behaviour** (Free/Pro): The reference is an alphabetical, cross-linked glossary, also reachable from feature explanations. A control is a ranged value, discrete choice or command; its controller is the implementation method. Native Apple interfaces, DDC, network protocols and software processing can serve different operations on the same display. A range's neutral point is its unchanged value, not necessarily its midpoint or a physical measurement. Sliders, shortcuts and integrations can address the same operation. Defining or enabling a custom control does not establish device support. Ordinary controller selection/native brightness is Free; custom DDC/integration definitions are Pro ([controller licensing](https://betterdisplay.pro/guide/interface-reference/settings/displays/display/device-control/), [custom DDC licensing](https://betterdisplay.pro/guide/interface-reference/settings/displays/display/device-control/ddc/)).
- **FreeDisplay today**: 🟡 Partial. `Apps/OpenDisplay/Sources/AppModel.swift:16` defines a fixed hardware-control enum, and `Apps/OpenDisplay/Sources/AppModel.swift:55` chooses native/hardware/software brightness. There is no shared arbitrary-control definition, independent neutral/range mapping editor, network-controller assignment or searchable glossary. `Apps/OpenDisplay/Sources/LocalControlPanel.swift:33` exposes a small fixed HTTP command set.
- **Implementation notes**: M for a typed control descriptor containing units, neutral value, range, discrete values, read/write capability and operation-specific provider; L for a general integration framework. Keep requested, observed and unsupported states distinct. Reuse public SwiftUI for glossary/help; isolate private native/DDC providers.
- **Acceptance criteria**:
  - The same display can use DDC brightness and CoreAudio volume without one controller masking the other.
  - An unsupported custom code is visibly unverified; resetting a control uses its declared neutral, not an assumed 50%.
  - Help search and contextual links explain the active controller and applicable units.

### T02. Brightness, backlight and nits — [brightness](https://betterdisplay.pro/guide/technical-reference/brightness/) · [nits](https://betterdisplay.pro/guide/technical-reference/nits/) · [backlight](https://betterdisplay.pro/guide/technical-reference/backlight/)

- **BetterDisplay behaviour** (Free/Pro): Hardware brightness changes the device; software brightness changes image values; combined brightness spans both through one control. Below the useful hardware minimum, software dimming can continue while hardware stays at its boundary. Upscaling requires HDR headroom and suitable configuration. Percentages are positions within a control's range; neutral means unchanged. A nit is cd/m². Nits displays can be estimates derived from device data and user ranges, never newly measured luminance. SDR maximum, HDR peak and upscaling range are separate quantities; equal percentages across monitors need not match light output. Editing ranges changes mapping, not hardware capability. LCD illumination and self-emitting OLED brightness differ; backlight-off does not remove a desktop. Ordinary sliders and nits preferences are Free; upscaling is Pro ([sliders](https://betterdisplay.pro/guide/interface-reference/app-menu/device-menu/sliders/), [nits preferences](https://betterdisplay.pro/guide/interface-reference/settings/displays/display/general-settings/)).
- **FreeDisplay today**: 🟡 Partial. Native/DDC/fallback selection exists at `Apps/OpenDisplay/Sources/AppModel.swift:1280`; explicit software override is in `Apps/OpenDisplay/Sources/DisplayDetailView.swift:376`. Dimming combines gamma and an overlay at `Apps/OpenDisplay/Sources/AppModel.swift:692`; this is not a hardware-plus-software brightness continuum. No per-display nits mapping or calibrated neutral/range editor exists. **P0:** the main brightness path caches the requested fraction but clamps software output to at least 0.15 (`Apps/OpenDisplay/Sources/AppModel.swift:1374`); the tray displays that unclamped cache (`Apps/OpenDisplay/Sources/MenuBarView.swift:298`). Thus 0% and 10% can represent the same applied floor. Hardware readback still cannot establish actual backlight response; the explicit software override correctly acknowledges that limitation.
- **Implementation notes**: S to expose/clamp the effective software range consistently; M for combined mapping and estimated-nits metadata. Public CoreGraphics transfer tables/AppKit overlays; private DisplayServices/IOAVService for hardware. Preserve device readback and mark nits as calculated. Never treat black overlay as backlight-off.
- **Acceptance criteria**:
  - At the software floor the slider/OSD shows the effective position or clearly identifies a requested value; keyboard decrements do not silently accumulate below it.
  - A combined control crosses its hardware minimum continuously and restores neutral software processing when returning to the hardware range.
  - Missing luminance data shows unknown, and changing a nits range never claims to raise the panel's physical maximum.

### T03. Resolution, modes, HiDPI and physical size — [resolution](https://betterdisplay.pro/guide/technical-reference/resolution/) · [display-mode](https://betterdisplay.pro/guide/technical-reference/display-mode/) · [hidpi](https://betterdisplay.pro/guide/technical-reference/hidpi/) · [pixel-density](https://betterdisplay.pro/guide/technical-reference/pixel-density/) · [aspect-ratio](https://betterdisplay.pro/guide/technical-reference/aspect-ratio/)

- **BetterDisplay behaviour** (Free/Pro): Keep logical workspace, rendered/backing pixels, transmitted signal and native panel pixels separate. A typical 1920×1080 logical 2× mode renders 3840×2160, but that alone does not identify signal or panel dimensions. Mode identity includes refresh, rendering scale and possibly precision/output properties, not just width×height. Native/default markers and HiDPI/LoDPI filters describe available modes; filters never generate missing modes. HiDPI commonly uses 2× per axis, LoDPI 1×; neither is physical PPI. PPI needs panel dimensions, while equal pixel dimensions on different physical sizes produce different apparent UI sizes. Native-size overrides do not add physical pixels. Aspect ratio constrains filtering/generated choices; 1920×1080 and 3840×2160 are both 16:9. Rotation swaps axes; crop/stretch can change stream shape independently. Basic mode selection/filtering is Free; favorites, scale matching and protection are Pro ([mode licensing](https://betterdisplay.pro/guide/interface-reference/app-menu/device-menu/display-mode/)).
- **FreeDisplay today**: 🟡 Partial. Exact logical/backing/refresh/HiDPI fields and optional bit depth exist (`Packages/DisplayDomain/Sources/DisplayDomain/DisplayModels.swift:33`), but providers do not populate precision or signal-mode identity. The tray has native/default markers, compact/all lists, same-aspect slider stops and density counterparts (`Apps/OpenDisplay/Sources/TrayModeCatalog.swift:30`, `Apps/OpenDisplay/Sources/TrayModeCatalog.swift:93`, `Apps/OpenDisplay/Sources/TrayModeCatalog.swift:125`). Settings explain logical versus framebuffer sizes correctly (`Apps/OpenDisplay/Sources/DisplayDetailView.swift:91`). Mode application verifies a fresh exact match, keeps a crash-recovery marker and presents keep/revert (`Apps/OpenDisplay/Sources/AppModel.swift:3081`). **P0:** tray copy equates a native flag with no scaling and guaranteed sharpest output (`Apps/OpenDisplay/Sources/MenuBarView.swift:403`, `Apps/OpenDisplay/Sources/MenuBarView.swift:546`); that conclusion is not established by the metadata. Physical diagonal is reported, but no full PPI/physical-size editor exists (`Apps/OpenDisplay/Sources/AppModel.swift:1068`).
- **Implementation notes**: S for truthful native labels; M for separate signal/panel metadata and richer filters. Public CoreGraphics supplies mode and physical-size observations; unavailable fields must stay unknown. Retain exact fractional refresh and framebuffer matching. Avoid deriving native panel pixels from a supersampled framebuffer.
- **Acceptance criteria**:
  - Two equal logical sizes with different backing pixels or refresh remain distinguishable; rejected/stale modes never offer successful confirmation.
  - A 2× rendering example reports all known dimensions separately and does not imply a 4K physical panel.
  - HiDPI/LoDPI and aspect filters retain the current mode; missing physical dimensions disable PPI calculations.

### T04. Fixed and adaptive refresh — [refresh-rate](https://betterdisplay.pro/guide/technical-reference/refresh-rate/) · [adaptive-refresh-rate](https://betterdisplay.pro/guide/technical-reference/adaptive-refresh-rate/)

- **BetterDisplay behaviour** (Free/Pro): Refresh choices reflect the current resolution, HDR state and full connection; changes can alter the list. Fixed rates are Hz, while VRR/ProMotion represents a supported interval with actual timing varying by content and conditions. A maximum or range is not a promise that every frame uses its upper endpoint. Capture fps and panel Hz are different. Rate selection/reporting is Free; protection and group scale matching are Pro; connection-level extras need Apple Silicon ([refresh licensing](https://betterdisplay.pro/guide/interface-reference/app-menu/device-menu/refresh-rate/)). No numeric VRR range/default is specified in these reference pages.
- **FreeDisplay today**: 🟡 Partial. Fixed-rate alternatives are filtered against the current logical/backing size and HiDPI state (`Apps/OpenDisplay/Sources/TrayModeCatalog.swift:113`); `Apps/OpenDisplay/Sources/AppModel.swift:3149` uses guarded mode application. `DisplayMode` stores one `Double` rate, with no adaptive flag/minimum/maximum (`Packages/DisplayDomain/Sources/DisplayDomain/DisplayModels.swift:33`). Nonreported rate is displayed as unknown rather than invented (`Apps/OpenDisplay/Sources/AppModel.swift:1063`).
- **Implementation notes**: M. Public CoreGraphics for fixed modes; platform-specific/private discovery may be needed for actual variable intervals and connection timing. Represent fixed, adaptive-range and unknown separately. Do not reinterpret zero Hz as a known VRR range.
- **Acceptance criteria**:
  - 59.94 and 60 Hz remain distinct; changing resolution refreshes available rates.
  - A variable mode shows its supported range only when sourced from real metadata, and measured cadence is labeled separately from the maximum.

### T05. HDR, EDR, upscaling and clipping — [hdr](https://betterdisplay.pro/guide/technical-reference/hdr/) · [edr](https://betterdisplay.pro/guide/technical-reference/edr/) · [metal](https://betterdisplay.pro/guide/technical-reference/metal/) · [clipping](https://betterdisplay.pro/guide/technical-reference/clipping/) · [tone-mapping](https://betterdisplay.pro/guide/technical-reference/tone-mapping/)

- **BetterDisplay behaviour** (Free/Pro): HDR content, output mode and panel capability are separate. SDR has a conventional reference white; XDR is Apple's display/preset branding, not a universal link encoding. EDR expresses values above SDR white; headroom is a ratio (2× means twice current SDR white), and live versus potential maximum headroom can differ. Upscaling ordinary desktop luminance does not create HDR-mastered content and is unrelated to increasing image dimensions. HDR can change hardware-brightness availability. Software overlays can use Metal, including an upscaling fallback, with GPU cost. Clipping destroys highlight, shadow or channel distinctions; a near-white calibration pattern helps select a usable software limit but is not a colorimeter. Tone mapping fits content into available range and differs from clipping or SDR upscaling; no particular content-aware HDR mapping is guaranteed. Upscaling is Pro; signal-format changes that alter SDR/HDR encoding are Pro ([sliders](https://betterdisplay.pro/guide/interface-reference/app-menu/device-menu/sliders/), [color mode](https://betterdisplay.pro/guide/interface-reference/app-menu/device-menu/color-mode/)).
- **FreeDisplay today**: 🟡 Partial. Labs exposes built-in EDR-potential gating (`Apps/OpenDisplay/Sources/AppModel.swift:785`), a Metal EDR trigger (`Apps/OpenDisplay/Sources/XDRBrightnessController.swift:96`) and gamma-table boost. The policy caps boost at 3.2 and defaults its one-click fraction to a nominal 2× at full headroom (`Packages/TopologyCore/Sources/TopologyCore/XDRBrightness.swift:18`). It documents clipping, not calibrated HDR mapping. Current/potential headroom are correctly separate in `Apps/OpenDisplay/Sources/AdvancedDisplayToolsView.swift:29`. No HDR output switch, external HDR upscaling, clipping calibration or general tone-mapping pipeline exists. **P0:** `hdrEnabled` defaults to false (`Packages/DisplayDomain/Sources/DisplayDomain/DisplayModels.swift:115`), the live provider never supplies it (`Providers/CoreGraphicsProvider/Sources/CoreGraphicsProvider.swift:308`), yet the scene planner can declare HDR-off already satisfied (`Packages/SceneEngine/Sources/SceneEngine/ScenePlanner.swift:172`). Unknown output state is being represented as confirmed off.
- **Implementation notes**: S/M to make HDR observations optional/capability-aware; L for reliable external upscaling and calibration. Metal and NSScreen EDR are public; connection HDR switching may need isolated private display interfaces. Reassess live headroom across power, preset and topology changes; never generalize a fixed 1600/500 ratio to every panel.
- **Acceptance criteria**:

### T08. Signal encoding, depth, framebuffer and color spaces — [rgb](https://betterdisplay.pro/guide/technical-reference/rgb/) · [bit-depth](https://betterdisplay.pro/guide/technical-reference/bit-depth/) · [framebuffer](https://betterdisplay.pro/guide/technical-reference/framebuffer/) · [color-mode](https://betterdisplay.pro/guide/technical-reference/color-mode/) · [ycbcr](https://betterdisplay.pro/guide/technical-reference/ycbcr/) · [chroma-subsampling](https://betterdisplay.pro/guide/technical-reference/chroma-subsampling/) · [color-range](https://betterdisplay.pro/guide/technical-reference/color-range/) · [color-space](https://betterdisplay.pro/guide/technical-reference/color-space/) · [color-gamut](https://betterdisplay.pro/guide/technical-reference/color-gamut/)

- **BetterDisplay behaviour** (Free/Pro): Color Mode presents system-supported combinations of RGB/YCbCr encoding, component precision, chroma sampling, full/limited range and SDR/HDR encoding. - **Acceptance criteria**:

  - Unknown panel precision stays unknown even with a float framebuffer; unsupported combinations cannot be applied.
  - P3/PQ LUT interpretation is explicit and round-trips without silently treating all input as sRGB.

### T15. ### T19. Stream exposure, saturation, vibrance, hue and blending — [exposure](https://betterdisplay.pro/guide/technical-reference/exposure/) · [saturation](https://betterdisplay.pro/guide/technical-reference/saturation/) · [vibrance](https://betterdisplay.pro/guide/technical-reference/vibrance/) · [hue](https://betterdisplay.pro/guide/technical-reference/hue/) · [blend-mode](https://betterdisplay.pro/guide/technical-reference/blend-mode/)

Saturation controls color intensity relative to gray; stream neutral is **1.00**, distinct from monitor percentage scales. It may be provided by hardware, display processing or stream filters, without equivalence between paths. Vibrance changes saturation selectively and cannot widen the physical gamut. Hue shifts color family without selecting a profile or calibrating the panel. Stream blend mode combines adjusted and original images; blend strength controls contribution. Multiply generally darkens, while screen generally lightens; “screen” here is an operation, not a device. Software ranged adjustments/video filters are Pro; ordinary hardware controls retain their own gates ([image adjustments](https://betterdisplay.pro/guide/interface-reference/app-menu/device-menu/image-adjustments/), [video filters](https://betterdisplay.pro/guide/interface-reference/app-menu/device-menu/video-filters/)). Other numeric defaults/ranges are not given here.
- **FreeDisplay today**: ⬜ Missing these individual filters/controls. `Providers/CaptureProvider/Sources/CaptureImageTransform.swift:6` performs crop, flip, rotation and optional cube only, and `Apps/OpenDisplay/Sources/CapturePanel.swift:200` exposes exactly that subset. A LUT can encode a look but is not an editable exposure/saturation/vibrance/hue/blend UI. The fixed hardware enum also omits saturation (`Apps/OpenDisplay/Sources/AppModel.swift:17`).
- **Implementation notes**: M/Low for CoreImage filters on captured content; M/High for added DDC saturation; L for display-wide equivalents. Specify linear versus encoded working space, filter order and blend reference image, and expose neutral/reset independently of LUT selection.
- **Acceptance criteria**:
  - Neutral filter settings preserve input; +1/−1 exposure has the expected light-value scaling in the declared working space.
  - Saturation 1.00 is neutral, zero yields gray, and vibrance does not act as a renamed saturation control.
  - Blend strength zero preserves the original; stream-only changes do not modify the desktop or monitor settings.

### T20. Gain, black level and color temperature — [color-temperature](https://betterdisplay.pro/guide/technical-reference/color-temperature/) · [gain](https://betterdisplay.pro/guide/technical-reference/gain/) · [black-level](https://betterdisplay.pro/guide/technical-reference/black-level/)

Software channel controls are separate under Image Adjustments. - **Acceptance criteria**:

### T32. EDID and DisplayID — [edid](https://betterdisplay.pro/guide/technical-reference/edid/) · [displayid](https://betterdisplay.pro/guide/technical-reference/displayid/)

- **FreeDisplay today**: 🟡 Partial planning/export only. `Apps/OpenDisplay/Sources/AdvancedDisplayToolsView.swift:50` exports a HiDPI plan; `Packages/TopologyCore/Sources/TopologyCore/DisplayConfigurationTools.swift:85` validates logical dimensions up to 8192 and produces a 2× backing proposal plus recovery instructions. This adds no physical mode. There is no privileged override installer, flexible-step generator, NVRAM clearer or system-display-reset workflow. `SMAppService.mainApp` in `Apps/OpenDisplay/Sources/LaunchAtLogin.swift:50` registers login launch; it is not a privileged helper. `scripts/bundle-helper.sh` packages the CLI and does not establish privileged-service support.
- **Implementation notes**: L/High for transactional override installation through an authenticated, narrow ServiceManagement/XPC helper; M for aspect-preserving planning. Back up exact prior configuration, separate staged/applied/activation-pending states and provide recovery before reboot. NVRAM/reset is niche and must never be a routine mode-selection step.
- **Acceptance criteria**:
  - Editing/generating/exporting modes leaves live output unchanged until a distinct approved application step.
  - A rejected helper operation or required reboot remains pending/failed, never “mode enabled.”
  - Reset describes app preferences versus system display configuration versus firmware scope, with original data recoverable after failure.

### T34. Persistent display identification — [display-identification](https://betterdisplay.pro/guide/technical-reference/display-identification/)

- **BetterDisplay behaviour** (tier unspecified in this entry): Recognition can use system UUID, vendor/model/serial, name, connection location or EDID strategy. UUID is not a printed serial number. Identical monitors can expose indistinguishable data, and one physical monitor can acquire a different system identity after connection/install changes. Imported settings may therefore require explicit transfer to a newly recognized display. A custom name is primarily a readable label, not proof of physical identity. Additional Settings owns identification preferences.
- **FreeDisplay today**: 🟡 Partial. Persistent records support aliases/tags/pairing and scored fingerprints (`Packages/DisplayDomain/Sources/DisplayDomain/DisplayModels.swift:148`; `Packages/TopologyCore/Sources/TopologyCore/DisplayRegistry.swift:114`). Public provider fingerprints contain vendor/product/serial/physical size (`Providers/CoreGraphicsProvider/Sources/CoreGraphicsProvider.swift:339`) and observations prefer CG UUID with transient-ID fallback (`Providers/CoreGraphicsProvider/Sources/CoreGraphicsProvider.swift:331`). No user-selectable identification strategy or settings-transfer UI exists. **P0:** registry recognition takes the first serial match without qualifying vendor/model, then takes a single highest score without rejecting equal-score candidates (`Packages/TopologyCore/Sources/TopologyCore/DisplayRegistry.swift:148`, `Packages/TopologyCore/Sources/TopologyCore/DisplayRegistry.swift:161`). Duplicate/placeholder serials or tied fingerprints can attach preferences to the wrong record; this is separate from EDID and DDC service matching defects.
- **Implementation notes**: M. Prefer explicit ambiguity over an arbitrary match; qualify serial evidence, prevent one stored record from being assigned to two simultaneously present endpoints and retain provenance for location/EDID evidence. Provide a reviewable transfer/re-pair action without discarding the old record.
- **Acceptance criteria**:
  - Identical serial-less panels and two vendors reusing the same serial cannot silently share a persistent preference record.
  - Renaming changes only the label; replugging changes transient IDs without silently moving settings to another device.
  - Explicitly transferring settings preserves an audit trail and leaves ambiguous automatic recognition unresolved until chosen.

### T35. GPU and connection diagnostics — [gpu](https://betterdisplay.pro/guide/technical-reference/gpu/) · [link-bandwidth](https://betterdisplay.pro/guide/technical-reference/link-bandwidth/) · [dsc](https://betterdisplay.pro/guide/technical-reference/dsc/) · [hdcp](https://betterdisplay.pro/guide/technical-reference/hdcp/) · [dpcd](https://betterdisplay.pro/guide/technical-reference/dpcd/)

- **BetterDisplay behaviour** (tier unspecified): GPU rendering capacity and link bandwidth are separate limits; a framebuffer can fit in memory yet exceed the cable's payload capacity. Software effects/streams cost GPU work. Connection information can report rate, lanes and bandwidth from macOS; raw Gbps includes protocol/encoding overhead, not all pixel payload. More resolution/Hz/depth usually increases demand; DSC or chroma subsampling changes it. DSC is low-latency visually lossless compression, not mathematically identical values; supported DSC is distinct from currently active DSC. HDCP reports protocol versions for protected transport, not calibration/compression or a guarantee a particular player/service permits playback. DPCD registers describe DisplayPort link capability/configuration/status, unlike display-identifying EDID. Missing DPCD may mean the path cannot expose it, not that DisplayPort is absent. These reports are not cable-quality measurements or promises that every mode works.
- **FreeDisplay today**: ⬜ Missing detailed link/DSC/HDCP/DPCD and GPU-load reports. `Apps/OpenDisplay/Sources/AppModel.swift:1045` reports names, identifiers, logical/backing dimensions, rate, rendering density and diagonal only. `Providers/CoreGraphicsProvider/Sources/CoreGraphicsProvider.swift:321` labels most external transports unknown. Headroom diagnostics are separate and do not fill this gap (`Apps/OpenDisplay/Sources/AdvancedDisplayToolsView.swift:29`).
- **Implementation notes**: M for read-only metadata schema/UI; L/High for private DPCD/IOAV/system diagnostics across adapters. Use public Metal device information where relevant; every optional link field needs source, unit, supported/active distinction and unknown state. Avoid speculative bandwidth calculators presented as negotiated link readback.
- **Acceptance criteria**:
  - Raw link rate and estimated payload are separately labeled with lanes/overhead assumptions.
  - DSC capability and active compression, HDCP versions and actual playback authorization remain separate fields.
  - An unreadable DPCD route shows unavailable data without concluding the monitor lacks DisplayPort.

### T36. HDMI, DisplayPort, USB-C and Thunderbolt — [hdmi](https://betterdisplay.pro/guide/technical-reference/hdmi/) · [displayport](https://betterdisplay.pro/guide/technical-reference/displayport/) · [usb-c](https://betterdisplay.pro/guide/technical-reference/usb-c/) · [thunderbolt](https://betterdisplay.pro/guide/technical-reference/thunderbolt/)

- **BetterDisplay behaviour** (reference concepts, no standalone tier): HDMI transports video/audio/related data; resolution, refresh and HDR depend on both endpoints, cable and adapters, not only connector/version. Video, DDC and CEC support are independent. DisplayPort can use its native connector or USB-C Alternate Mode; DP-to-HDMI conversion can change which commands pass. USB-C describes connector shape, not guaranteed data speed, power delivery or native video support. USB4/Thunderbolt can carry displays, but a USB-only cable/device is not automatically a video path. Thunderbolt shares a link for display and other data; modern USB-C shape alone does not establish Thunderbolt. Docks can expose native display, converted or DisplayLink outputs with different scaling/bandwidth/control capabilities. Diagnose the complete Mac–dock–cable–display route.
- **FreeDisplay today**: 🟡 Partial schema, missing route discovery/diagnostic UI. `Packages/DisplayDomain/Sources/DisplayDomain/DisplayModels.swift:18` enumerates HDMI, DP, USB-C DP, Thunderbolt, dock and KVM, but `Providers/CoreGraphicsProvider/Sources/CoreGraphicsProvider.swift:321` normally supplies unknown for externals. A display being enumerated does not validate any transport control. Current information UI does not reconstruct the chain.
- **Implementation notes**: M/Low for explanatory UI and user-supplied route annotations; L/High for reliable automatic topology from vendor/private registry data. Distinguish discovered, user-entered and inferred route information and invalidate capability evidence after path changes.
- **Acceptance criteria**:
  - An unknown connector/adapter route stays unknown; USB-C never automatically implies Thunderbolt or DisplayLink.
  - Moving the same display through a different dock re-evaluates command support and modes without losing its confirmed physical identity.
  - Diagnostic export separates successful video transport from DDC/CEC availability.

### T37. Integration scripts, regex, notifications, polling and timeouts — [polling](https://betterdisplay.pro/guide/technical-reference/polling/) · [shell-script](https://betterdisplay.pro/guide/technical-reference/shell-script/) · [regular-expression](https://betterdisplay.pro/guide/technical-reference/regular-expression/) · [distributed-notification](https://betterdisplay.pro/guide/technical-reference/distributed-notification/) · [timeout](https://betterdisplay.pro/guide/technical-reference/timeout/)

- **BetterDisplay behaviour** (Free/Pro): Control Integration can execute a configured command and interpret its output. The action labeled “Shell script (zsh)” actually executes **`/bin/bash -c`**; the label does not select zsh. Placeholders are substituted before shell parsing, so quoting must be correct afterward. The app's Console parses app integration commands and is not a general shell. Regex selects readback values or Boolean results from actual returned text; regex syntax and shell quoting are separate. These technical pages do not specify match-group/failure parsing rules, so those must not be invented. Distributed notifications are local named interprocess messages with optional object/data, not Notification Center banners: Application Integration listens inbound, Control Integration sends outbound. Enabling one does not create a peer receiver or confirm delivery. Polling schedules reads; shorter intervals mean more requests. A timeout bounds one wait and is neither the interval nor measured latency. Timeout does not mean rejection or undo work already started; inspect actual state before uncertain retries. Predefined control integration and the event editor have no separate Pro gate; custom definitions and additional menu integration controls require Pro ([integration licensing](https://betterdisplay.pro/guide/interface-reference/settings/displays/display/device-control/control-integration/)).
- **FreeDisplay today**: 🟡 Partial app automation, ⬜ Missing generic outgoing control/script/regex/polling integrations and general inbound notification requests. Local HTTP exposes displays/brightness/reconnect-all and reports brightness as requested/unverified (`Apps/OpenDisplay/Sources/LocalControlPanel.swift:73`); listener lifetime is session/panel-scoped with token authentication (`Apps/OpenDisplay/Sources/LocalControlServer.swift:22`). Its five-second connection deadline does not imply rollback (`Apps/OpenDisplay/Sources/LocalControlServer.swift:53`). OSD events broadcast outbound (`Apps/OpenDisplay/Sources/OSDBroadcaster.swift:19`); the app's existing inbound notification just opens Settings (`Apps/OpenDisplay/Sources/OpenDisplayApp.swift:116`). CLI and App Intents are app commands, not a shell interpreter. Existing native-brightness polling is feature-specific (`Apps/OpenDisplay/Sources/AppModel.swift:1424`).
- **Implementation notes**: M for predefined integration actions; L for a general engine. Public Process, URLSession, NSRegularExpression and DistributedNotificationCenter suffice. Specify the actual interpreter honestly; prefer structured arguments, bounded output and explicit placeholder escaping. Keep read/write actions, parser rules, polling interval, operation deadline and unresolved-outcome status separate. Authorize incoming mutations and bound cancellation/retry behavior; cancellation cannot promise undo of external side effects.
- **Acceptance criteria**:
  - A Bash-only command succeeds only under an explicitly reported Bash interpreter; FreeDisplay never copies the misleading zsh label.
  - Readback extraction has deterministic capture-group/no-match/invalid-number behavior and rejects malformed values rather than replacing them with zero.
  - Polling does not overlap uncontrolled writes; timeout leaves an uncertain result until state is checked, and a sent notification is not recorded as acknowledged delivery.

- **BetterDisplay behaviour** (Free/Pro unspecified by this entry): Menu, display and group icons can be selected through a shared searchable SF Symbols picker. Symbols depend on the installed macOS library. Changing an icon changes the visual label, not capabilities or group behavior. The reference does not enumerate a default symbol or license gate.

The status item hardcodes `display` (`Apps/OpenDisplay/Sources/OpenDisplayApp.swift:120`), display rows choose symbols by class (`Apps/OpenDisplay/Sources/MenuBarView.swift:209`), and group schema has no icon field (`Packages/TopologyCore/Sources/TopologyCore/DisplayGroup.swift:14`). - **Acceptance criteria**:
  - Menu/display/group icon overrides persist independently and fall back gracefully when a symbol is unavailable.

### T39. Signing, notarization and download integrity — [code-signing](https://betterdisplay.pro/guide/technical-reference/code-signing/) · [notarization](https://betterdisplay.pro/guide/technical-reference/notarization/) · [sha-256](https://betterdisplay.pro/guide/technical-reference/sha-256/)

- **BetterDisplay behaviour** (not a feature-tier gate): A signature binds signed code/resources to a signer and detects changes; validity alone is insufficient without the expected identity. The guide names BetterDisplay's Developer ID Application signer as Istvan Toth, Team ID `299YSU96J7`. This identity is BetterDisplay-specific. Notarization is Apple's automated malware/signing assessment, not App Store review or proof of the intended publisher. Gatekeeper combines that ticket with other checks; stapling makes the ticket available offline. BetterDisplay says its installer DMG is signed/notarized from v5.1.1, with app-bundle verification separate. SHA-256 is a 256-bit digest usually rendered as 64 hex characters; comparison must use a trusted publisher's digest for the exact download bytes. Filename, size or a self-calculated hash alone does not identify the developer; an unsigned file can still match trusted published bytes.
- **FreeDisplay today**: ➖ BetterDisplay identity/version/DMG claims must not transfer to FreeDisplay. 🟡 Partial analogous release tooling: `scripts/release-signed.sh:69` signs nested code/app with Developer ID and verifies it; `scripts/release-signed.sh:117` submits a ZIP, staples the app and re-zips it, then produces a Sparkle appcast. No release execution or existing artifact authenticity was verified in this review. No SHA-256 publication step is present. **P0:** Gatekeeper assessment failure is swallowed by `spctl ... || true` before a success message (`scripts/release-signed.sh:134`); the script also chooses the first Developer ID identity if none is specified (`scripts/release-signed.sh:42`). FreeDisplay release identity is not pinned by that fallback.
- **Implementation notes**: S/M, Low API risk but release-critical. Require the expected FreeDisplay team/signer, fail the release gate on failed signature/notary/staple/Gatekeeper checks, and generate the checksum after the final archive bytes exist. Publish the expected identity and digest through the project's trusted release channel. Use FreeDisplay's branding and credentials; retain required GPL notices without copying BetterDisplay assets.
- **Acceptance criteria**:
  - A wrong signer or failed Gatekeeper assessment blocks a release-ready result; app and container are independently checked when both are distributed.
  - A stapled release opens under normal offline Gatekeeper assessment, verified on an actual release artifact later.
  - The published 64-hex checksum matches final download bytes and changes if any byte changes; a digest match is never described as signer authentication by itself.
