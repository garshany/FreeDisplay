# FreeDisplay Clock Mode

Per-display Clock Mode is a recurring brightness policy available on macOS 14 and later. In Settings, select each display with Add Display Recipe, choose its current controller, and add Day/Evening schedule points with independently chosen absolute values. Choose Instant for fixed plateaus, Ramp for an approach ending at the next point, or Continuous for interpolation over the complete gap. Ramp duration is configurable in minutes; zero steps at the point. There is no new schedule-count limit, retry budget or timeout. The app retains its existing five-second sampling cadence, so this is not an exact-time trigger service.

Brightness is the shared automation model's normalized 0–1 range, presented as 0–100 percent of that controller's range. It is not measured nits and adds no HDR or upscaled range. The shared AutomationEngine resolves the stable display identifier, selects the requested route, and reports transport/readback outcomes. A native, DDC, or hardware-only request refuses if the configured current route cannot carry it; it never substitutes software. Configure a display's controller in its existing brightness controls first. The public-only build offers software brightness, and honestly refuses private native/DDC routes.

Adding a display proposes the app's currently known brightness as an editable Restore value, with no schedule points and no write. Check this against the actual display and choose the intended controller before enabling the schedule. This value is an explicit brightness-only return recipe, not a transaction snapshot. Apply Now runs the current recipe once through the same command model and range used by recurring execution; repeating it requests the same final state. Restore turns scheduling off first, then applies that display's declared return value. Other recipes' current values are retained, and each Restore remains accessible while scheduling is off. Offline/ambiguous identities and unavailable routes are reported, without another target or controller being chosen. Restore itself does not alter contrast, color, geometry, ICC, HDR or group configuration.

With a per-display configuration present, the old shared external-DDC Clock schedule is inactive. Its stored points remain intact for compatibility; Use Legacy Shared Schedule explicitly returns to that mode. Removing the final display does not silently re-enable the old shared schedule. An invalid new-format configuration also cannot reactivate it. An explicitly configured display is reserved from Adaptive brightness even while its schedule is off; remove its recipe to return ownership to Adaptive. Adaptive warmth remains independent.

## Calendar and sleep

An empty time-zone identifier follows this Mac's time zone on each evaluation. A valid named time zone stays fixed while travelling; an unknown identifier refuses evaluation. Calendar evaluation uses the actual previous/current/next civil days, including days with 23 or 25 hours. The first valid time after a spring DST gap replaces a missing wall time; an autumn repeated wall time uses its first occurrence only. Ramps/continuous transitions interpolate real elapsed time, so the repeated hour cannot roll the schedule backwards. Coincident resolved points refuse instead of picking an array order. Fixed-time offsets retain the old wrapped-minute meaning. Solar events resolve for each civil day at the supplied coordinates, using that day's zone offset; absent location or unavailable sunrise/sunset contributes no point. Missing solar events are not replaced with invented times; fixed points can still govern.

The selected wake policy is either Apply current interval; skip missed transitions or Pause until Resume is pressed. The editor initially selects current-interval catch-up, reflecting the old scheduler's convergence behaviour. Neither policy replays an event queue or wakes the Mac. No writes are issued while the machine/display is asleep. The pause is recorded before any awaited wake refresh, and dispatch checks current policy again after startup/route discovery. Unavailable displays are re-evaluated at the existing cadence; topology return invalidates previously settled requests. No new wake delay or retry threshold is introduced.

macOS Shortcuts time-of-day triggers have their own OS-dependent availability, confirmation and missed-trigger behaviour; they do not acquire Clock Mode's catch-up semantics. FreeDisplay does not add, enable or claim to test those system triggers here.

## Manual and competing controls

A manual brightness request through FreeDisplay holds the explicit schedule until the next resolved schedule point, including across sleep within the same interval. Resume clears manual holds and wake pause. Shift safe startup suppresses all recurring writes for that app session, including after wake. Apply Now and Restore remain explicit user actions.

An active brightness-sync group (including Default) or active app preset blocks recurring, Apply Now and Restore writes for that display. The UI reports that hold or a shared command refusal. Pause the competing policy explicitly to use independent scheduled levels. Clock writes bypass group leadership/offset learning only after checking that no group owns the target; they do not silently change group settings. Already dispatched hardware writes can still finish after a toggle or configuration change. Other applications, monitor buttons and macOS controls are not continuously observed by this policy and can change actual brightness. A wake/current-state catch-up reasserts the current interval, subject to manual holds.

Readback is controller/software state, not a physical luminance measurement. Hardware, installed Shortcuts discovery, wake notifications and visual layout require separate real-device validation. This implementation was verified with deterministic injected-date/time-zone and fake-environment unit tests and builds only.
